# 部署手册

适用对象：把"蒙电信产助手"装进内网终端并长期运维的人。所有路径、命令、界面文案都取自本仓库当前实现，未经实现的能力不会被写成"应该这样做"。

**交付时要按 sha256 核对，不要按字节数**：连续三次（10-15 的 13:19 / 13:52 / 14:26）主程序字节数都是 12,729,008、`.app` 恒为 14.00 MiB，而那三批的 Rust 内容并不相同（后两批分别才含 §8 第 23、24 条那两处修复）；10-16 17:2x 那批换成 12,762,048、本轮再变成 12,762,064，只涨 16 字节却是完全不同的密钥装配逻辑——反过来又说明"字节数变了/没变"都不能当判据。判据只有包内二进制的 sha256 与运行时行为（见 §2 那条隔离 `HOME` 的核对方法与《交付状态与验收》§2）。

`tauri.conf.json` 的 `bundle.targets` 列了 7 种目标，跨平台机器上多余目标会被忽略；在 macOS 上必须显式 `--bundles app,dmg`，否则 CLI 会尝试为其它平台打包。**另外两条本轮实撞的构建期事实**：① **`--bundles dmg` 单独跑会在打完 dmg 之后删掉 `bundle/macos/*.app`**（日志里那句 `Cleaning …/蒙电信产助手.app` 不是清缓存），所以两个产物必须一次写全，不要分两次跑；② dmg 步骤会因上一轮遗留的挂载卷或临时镜像失败（`failed to run …/bundle_dmg.sh`），打包前先 `ls /Volumes/` 清掉 `dmg.xxxxxx`（`hdiutil detach`）并删除 `bundle/macos/rw.<pid>….dmg`。完整步骤在《交付状态与验收》§10 第 19 步。

### 1.3 未签名事实

本机构建没有开发者证书与公证，产物是 ad-hoc/未签名（`codesign -dv` 报 `Signature=adhoc`、`flags=0x20002(adhoc,linker-signed)`、`TeamIdentifier=not set`）。分发到其它 Mac 时 Gatekeeper 会拦；内网如需可信分发，必须由组织用企业证书签名并对 `.app` 做公证后重新打包。

这条未签名事实还有一个直接后果，运维必须知道：macOS 把钥匙串条目的访问 ACL 绑在签名身份上，身份每重打包就变一次，所以**只要用钥匙串就必然每换一次包弹一次授权框**（连"探测安全存储是否可用"的那一次往返也算）。本包因此在 2026-10-17 起把 DB 主密钥改成默认放本机 0600 文件，不再访问钥匙串（仅遗留库迁移那一格读一次）；如果哪天回退到系统安全存储，就必须同时把 Developer ID 签名 + `keychain-access-groups` 写进装机基线，否则每台机器每次升级都要人工点一次"始终允许"。

## 2. 首次安装与初始化

1. 安装并启动 → 若这是本机第一次装配，界面先停在**密钥存放位置确认页**（只有两个按钮、零个输入项，见本节第 3 步）；同意之后才进入建库页。建库页的界面在 2026-10-16 那批按静态原型重做过：昵称输入框已删除，昵称由后端用设备名自动生成（内部标识形如 `MDA-…`，用户不需要记住它），现在只有"设置密码 + 确认密码"两项。
2. **主密码没有任何强度要求（2026-10-17 L 轮起，交付方决定）**：建库、改密、新增使用者、管理员重置四种口令只要求"非空且不只含空格"，`a`、`12345678`、`password` 都能建库，界面上也不再显示位数要求或策略提示。`master_password_min_length`（出厂 12，内置下限 10 不可下穿）**从这一个版本起只作用于导出容器口令**，对主密码路径没有任何读者——运维在系统组件页看到的这一行现在叫「导出容器口令最小长度」，看到它别当成"用户必须输 12 位才能建库"。**这是需求 §3.2 复杂度要求的一次显式偏离，安全后果是台账可以由一枚一秒就能猜中的主密码保护**，口径见《密钥生命周期与加密边界》§3 的偏离声明与交付文档 §1-L；交付方已知情并选定，装机方若要恢复，改回一处闸门 + 前后端各加回一行提示，约 30 分钟，不改数据库。空口令仍然会被拒（错误码 `WEAK_PASSWORD`、文案"主密码不能为空，也不能只输入空格。"），这是目前认证页上唯一还能看到 `WEAK_PASSWORD` 的原因。
3. **数据库主密钥的默认存放位置就是数据目录里的 `vault.device.key`（0600），本包不访问系统安全存储**（这是需求 §7.2 首选存储的一次显式偏离，理由与代价见《密钥生命周期与加密边界》§4.7）。启动第一步只看两件事：本机有没有密钥文件、有没有 `vault.db`。
   - 全新安装（两者都没有）：进程活着、**一个字节都不写**，日志只有两行——`尚未获得显式同意：未写入任何密钥文件…` 与 `本机尚无密钥文件（原因=fresh）…`，界面停在确认页。点「我了解风险，使用本机文件密钥」才生成 32 字节密钥并写 `vault.device.key`（0600）+ `keystore-fallback.flag`（内容 `file-0600`）+ `keystore-consent.flag`（只有一个 ISO 时间戳），随后装配保险库、记一条 `system.device_key.consent` 审计（`detail=local-file-0600`，不含密钥内容）；点「退出」则进程结束、目录里不留任何文件。
   - **升级旧版本留下的库**（`vault.db` 在、本机没有密钥文件）：这是**唯一**会碰到钥匙串的一格。日志出现 `检测到保险库文件但没有本机密钥文件：尝试从系统安全存储读取旧密钥以完成一次性迁移（未签名构建可能弹一次授权对话框）`，随后 macOS 弹一次「"蒙电信产助手"想要使用你储存在钥匙串的"com.mda.assistant"中的机密信息」，**并要求输入登录钥匙串密码**（adhoc 签名的身份每换包就变，macOS 不认旧 ACL）。现场处置：输入登录钥匙串密码 + 点**允许**（不需要点"始终允许"，本包此后不再访问那条条目），界面进入确认页（标题变成"这份保险库的密钥还在系统安全存储里"，按钮是「我了解风险，迁移到本机文件密钥」），点它才会把旧密钥原样复制成 0600 文件；钥匙串里那条**保留不删**，是唯一的回滚凭据。
   - **那一格点了"拒绝"会怎样**：进程不再继续装配，日志出现 `保险库文件已存在、本机没有密钥文件、系统安全存储也没读到密钥…不会生成新密钥，换掉设备密钥会让已有数据永久无法解密` 与错误码 `DEVICE_KEY_LOST_VAULT_INTACT`，界面停在失败页「取不到数据库密钥」。**这是设计行为，不是新故障**。实测（2026-10-17，用真实库的**副本**跑的）：拒绝后数据目录里不会多出 `vault.device.key`、`keystore-fallback.flag`、`keystore-consent.flag` 中的任何一个，`vault.db` 的 sha256 与测试前逐字节相同。恢复办法见 §5.2。
   - **不要再按"每次换包都要人工点一次始终允许"写装机基线**：那条现象的根因（重打包换签名身份 → 钥匙串重新索要授权，以及"探测安全存储是否可用"本身就会弹框）已经通过"不碰钥匙串"消除。只有回退到使用系统安全存储的构建时，才需要重新引入 Developer ID 签名 + `keychain-access-groups`。
4. 确认页在两种问法下文案不同，运维要认得出：`reason=fresh` 是"数据库主密钥要落在本机文件"，`reason=legacy-vault` 是"这份保险库的密钥还在系统安全存储里"。安全状态页与「此刻」面板按 `keystore_diagnostics.deviceKeyConsent` 区分来源：`consented`=本次经显式同意（绿色），`legacy-file`=加设闸门之前的旧版本遗留（"本机没有本次显式同意的记录"），未确认=黄色"未确认"。`keystore_diagnostics` 现在**不再探测任何后端**，`dbKeyStore` 只会是 `local-file-0600` 或 `unknown`。
   - 该文件**没有第二份拷贝**：删掉它 = 数据库永久不可读。
   - **同意闸门本身一条没松**：无论哪种问法，都必须由操作者在 `DeviceKeyConsentScreen` 上当场点确认按钮才会写入，未点之前启动阶段一个文件都不写、库也不装配；该页只有两个按钮、零个输入项。要告知使用者这页的含义：0600 只挡住**其他系统账户**，同一个账户下运行的任何程序都能读到这个文件——这是不换 Developer ID 签名换来的代价；一旦选了"退出"又没建第二名可信使用者，就没有第二条恢复路径。
   - **另一条硬闸门**：新建密钥只允许在"本机还没有 `vault.db`"时发生。若库已经在而密钥取不到（密钥文件被删、或遗留库那一格的钥匙串读取被拒），启动直接以 `DEVICE_KEY_LOST_VAULT_INTACT` 失败，既不进确认页也不写任何文件；即使从命令侧以"操作者已同意"的身份走创建路径，创建密钥那一处还会再判一次库在不在并拒绝（测试 `consented_file_key_creation_is_refused_while_a_vault_exists`）。这条不可绕过，目的是不让"让应用起来"这个动机把已有数据永久锁死。
   - **构建批次要求**：确认页本身在 **2026-10-15 14:26:48 之前**的 release 包上是**打不开**的——那一类包在全新机器（无密钥文件、无同意记录）启动时，界面还没渲染就先崩：`rc = -6`（SIGABRT），实测 494 ms 退出（原因见《交付状态与验收》§8 第 24 条：启动时并发发出的 `get_theme` 在"全局状态尚未装配"时 panic，而 release 配置是 `panic = "abort"`）。**部署前请用包内二进制的 sha256 与发布记录比对**，不要只按版本号判断；当前批次（2026-10-17 13:24）的值是 `f2b92b0a…eb222`（完整值见 §1.1）。
   - **一条不需要动你真实钥匙串的核对方法**（本轮实测走的就是它）：在隔离的临时 `HOME` + 空数据目录下直接跑包内二进制，看它是否"活着停在确认页且一个文件都不写"。`HOME=$(mktemp -d) MDA_DATA_DIR=$(mktemp -d) "…/Contents/MacOS/mon-dian-assistant"`，期望日志按序**只有**这两行：`尚未获得显式同意：未写入任何密钥文件，需要操作者确认后才能继续` → `本机尚无密钥文件（原因=fresh）：等待操作者显式确认后才会写入，未获得同意前不访问也不写入任何密钥存放位置`，且数据目录里**没有任何文件**、日志里**不出现任何访问系统安全存储的痕迹**。判据别只看日志：用窗口表确认界面真的起来了（`CGWindowListCopyWindowInfo` 按 pid 过滤，主窗口应在），要看第一帧文字就给 app 元素设 `AXEnhancedUserInterface = true` 再走无障碍树。**注意 `System Events` 的 `count of windows` 在这台机器上会全局返 0，不能当"没渲染"的证据**。
   - 想把"点同意→写出 0600 文件→重启不再询问"整条都证：同一个空数据目录别删，第二次启动（同一 `HOME`/`MDA_DATA_DIR`）日志应只剩 `数据库已就绪：schema v5` 与 `全局快捷键已注册` 两行。本轮实测：同意后 `vault.device.key` 是 32 字节、权限 `-rw-------`，第二次启动零密钥存放位置访问。
   - **这个隔离办法测不了"遗留库迁移"那一格**：那一格需要钥匙串里真的存在 `com.mda.assistant` / `vault-db-key-v1` 条目，而 macOS 的钥匙串搜索列表 / 默认钥匙串由 securityd **按登录用户（uid）**管理，不跟 `HOME` 走。要证它必须在真实登录用户下跑，而且要输一次登录钥匙串密码——**请先用数据目录的副本试，别拿真库试**（本轮就是这么做的：把 `vault.db` 三件套复制到 `/tmp`，`MDA_DATA_DIR` 指过去，原目录一个字节没动）。

## 3. 浏览器扩展与安全填充

### 3.1 步骤

1. 在浏览器里以"解压的扩展程序"方式加载扩展，记下 Chrome/Edge 分配的 **32 位小写字母扩展 ID**。
2. 桌面端：系统管理 → 安全设置 → 设置项 → 在 `extension_id` 里填入该 ID 并保存。空值或非 32 位小写会被后端拒绝（`fill_host::is_valid_extension_id`）。
3. 同一页面点"安装宿主清单"：程序生成 `com.mda.fillhost.json`，`allowed_origins` 精确写成 `chrome-extension://{ID}/`，并把它放进各浏览器的 `NativeMessagingHosts` 目录。
4. 扩展通道就绪后，快捷启动器的"打开并安全填充"才可用；未就绪时界面如实显示"未就绪"，动作降级为"打开网站 + 手动输入"。

清单目录（`fill_host::browser_manifest_dirs`）：

| 平台 | Chrome | Edge | Chromium |
|---|---|---|---|
| macOS | `~/Library/Application Support/Google/Chrome/NativeMessagingHosts` | `…/Microsoft Edge/NativeMessagingHosts` | `…/Chromium/NativeMessagingHosts` |
| Linux | `$XDG_CONFIG_HOME/google-chrome/NativeMessagingHosts` | `…/microsoft-edge/…` | `…/chromium/…` |

### 3.2 部署注意

- 宿主进程通过 `MDA_DATA_DIR` 找到与桌面端相同的数据目录；单实例通道信息在 `host-channel.json`。
- 填充票据一次性、绑定"用户 + 凭据 + 来源站点 + 会话"，重放会被拒（`crypto::tokens::tests`）。
- `quick_launcher_fill_enabled=false` 或 RBAC 无相应权限时，填充一律不可用；快捷启动器没有任何绕过 RBAC 的特权接口。

## 4. 更新通道

两条通道并存：**HTTPS 发布源**（原有）与**局域网镜像**（同网段互相发现）。两者用同一份已签名清单、同一套验签与 SHA-256 校验，差别只在"包从哪取"。

### 4.1 两条通道的共同约束

1. 后端白名单键 `update_source_url` 只接受 `https://` 开头（空值表示"未配置更新源"）；局域网手填源写在 `lan_manual_source`，**只接受私网 IP 字面量**（见 4.3）。`update_channel` 只接受 `stable`/`beta`。
2. 发布方对清单规范串签 Ed25519，规范串 = `canonical_of(version, channel, date, notes, packages)`（包按行排序、sha 小写）。
3. 客户端验签前**先重新导出规范串再比对**，所以"改包沿用旧签名"和"自造规范串"都会失败；公钥必须正好解出 32 字节，否则视为未配置并**拒绝安装**（不会跳过校验）。
4. 公钥下发二选一（**每条客户端都要配**，局域网通道也不例外）：
   - 环境变量 `MDA_UPDATE_PUBKEY=<base64(32 字节)>`
   - `MDA_CONFIG_DIR` 指向的目录里放 `update-release.pub`
5. 下载会强制比对清单里的 SHA-256，不一致即删除已下载文件。
6. 落盘文件名为 `downloads/<版本>-<平台>-<架构>.<扩展名>`，扩展名取自清单里包地址（白名单 `dmg/pkg/exe/msi/deb/rpm/AppImage`）。
7. **"安装"不会静默替换正在运行的自身**：权限 `SYS_UPDATE_INSTALL` + 近期二次认证后，会**重算一次 SHA-256**（防落盘后被替换），再交给系统默认程序打开安装包；macOS 上表现为 Finder 弹出 dmg，由操作者拖入「应用程序」后手动重启。界面文案据此写的是「打开安装包」，不是「安装并重启」。

### 4.2 局域网镜像

适用场景：内网没有 HTTPS 发布服务器，但同网段里只要有一台机器拿到了新版，其他机器应当能自己发现并取回来。

```
源机器（开启「在本机提供更新」）        客户端机器
<serve_dir>/manifest.json              监听组播 239.255.77.77:37020
<serve_dir>/packages/<包>.dmg  ──每 3 秒宣告──▶  收集 → 按版本排序
HTTP :8765  (/health /manifest          ◀──GET──  /manifest → 验签
             /package/<sha256>)         ◀──GET──  取包 → 比对 SHA-256 → 打开
```

- **拓扑是单源镜像**：只有开启托管的机器监听端口，客户端只做出站请求，不开任何入站端口。
- **安全边界靠签名，不靠信道**：局域网内仍是明文 HTTP，但清单必须验签、包必须对得上 SHA-256。明文只对**私网 IP 字面量**放行（`10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`、`::1`、`fe80::/10`、`fc00::/7`，以及 `::ffff:a.b.c.d` 归一后的 v4）；**域名一律不放行明文**，因为 DNS 解析结果无法提前确认落在私网。
- **内容寻址**：局域网模式忽略清单里的包 URL，按 `sha256` 向 `/package/<64 位小写 hex>` 取包。因此同一份清单既能给 HTTPS 通道用，也能给镜像用，不需要重签。
- **绝不降级**：源上版本低于本机时界面显示「低于本机」并禁用按钮（`is_newer` 判定），局域网通道不会把客户端拉回旧版本。

#### 托管目录结构

```text
<serve_dir>/
  manifest.json            # mda_release 产出的已签名清单，服务端原样下发
  packages/
    MDA-0.2.0-aarch64.dmg  # 文件名随意，扫描时算哈希与大小
```

开启托管前会先自检：清单能解析、公钥存在且验签通过、每个包文件存在且大小与清单一致。**任何一项不过就拒绝开启**并在界面显示原因码，绝不降级成"不校验也托管"——否则故障现场会从源机器扩散到所有客户端。

#### 生成密钥与签名（发布机离线执行）

```bash
# 一次性生成发布密钥（私钥 0600；已存在时拒绝覆盖，防误覆盖导致所有客户端验签失败）
mda_release keygen --out /secure/mda-release

# 把安装包放进托管目录后签名
mda_release sign --dir /srv/mda-lan --version 0.2.0 --channel stable \
    --notes "修复：备份恢复后的会话锁定。" \
    --key /secure/mda-release/update-release.key

# 可选项：--date YYYY-MM-DD / --platform / --arch / --pkg-url-prefix https://… / --signer
```

- 平台默认按扩展名推断（`.dmg`/`.pkg`→`macos`，`.exe`/`.msi`→`windows`，其余→`linux`），架构默认取执行 `sign` 的那台机器的架构，**交叉发布时必须显式给 `--arch`**。
- 包地址默认写成 `lan://<sha256>.<扩展名>`，只为保住可识别的扩展名（客户端据此决定落盘文件名）；局域网通道不看这个前缀。
- **私钥永远不进任何分发给终端用户的产物**，只在发布机上；委托给源机器的只是"已签名的清单 + 包"。
- 端到端自检（不依赖第二台机器）：

```bash
curl -i http://127.0.0.1:8765/health
curl -s http://127.0.0.1:8765/manifest | head -c 200
curl -s http://127.0.0.1:8765/package/<sha256> -o /tmp/got.dmg
shasum -a 256 /tmp/got.dmg     # 必须与清单里的 sha256 一致
```

#### 运维注意

- **端口**：默认 `0.0.0.0:8765`；被占用时自动改用系统分配的空闲端口，并在宣告里报真实端口，客户端不需要知道默认值。发现层用组播 `239.255.77.77:37020`，同时向子网广播补发一份作为降级。
- **macOS 防火墙**：首次监听会弹"是否允许接受传入连接"，必须点允许。非交互部署可预先放行：

```bash
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add "/Applications/蒙电信产助手.app"
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --unblockapp "/Applications/蒙电信产助手.app"
```

  没放行时服务照常起来，但只有本机可达；界面会显示自检失败的原因，不会假装一切正常。
- **企业网禁组播**（AP 隔离、IGMP snooping）时发现不到源：在「手填局域网更新源」里填 `IP:端口`（如 `10.8.3.21:8765`），该地址同样要过私网校验。
- **多网卡 / VPN**：宣告走 `IP_MULTICAST_IF` 指定的网卡，避免从 VPN 网卡发出去。仍不通时按上一条手填。
- **开关即时生效**：设置页关闭「局域网发现更新源」会当场停止监听并清空已发现的源；关闭「在本机提供更新」会当场停止监听端口。
- **休眠唤醒不暂停托管**：托管的是公开的签名包，不含任何秘密；锁定保险库也不暂停。
- 本轮**不做** mDNS/zeroconf、TLS、断点续传（中断即删半成品，可重试）；百兆内网 300 MB 约 30 秒。
- 未签名 dmg 会被 Gatekeeper 拦住（与 §1.3 现状一致）：界面打开后按右键 →「打开」放行一次。

私有化内网若暂时没有 HTTPS 源、也还没有可用的局域网源，就把 `update_source_url` 留空：界面显示"未配置"，检查更新给出明确不可用原因，**不会退回任意的 HTTP 或本地路径**——唯一的明文口子是上面那条受限的局域网通道。

## 5. 恢复场景（需求 §7.2 要求逐条有明确策略）

### 5.1 用户忘记主密码

- 没有任何后门口令。唯一路径：另一位**系统管理员**（`system_admin`）登录后执行"重置密码"（`admin_reset_password`），用**同一个 DEK**为该用户重新封装到新 `key_version`，台账仍可读，同时清零其失败计数与锁定。
- 若该用户是系统里唯一的管理员且口令丢失：**数据不可恢复**。可用路径只有从加密备份容器恢复（口令同样不可找回），或重建库重新录入。
- 运维上建议：任何生产终端至少保留两个管理员账号，并把 `create_backup` 的产物按 §5.4 异地存放。

### 5.2 设备密钥丢失 / 更换登录账户（含从旧版本的钥匙串库迁移）

自 2026-10-17 那批构建起，设备主密钥的常规位置是数据目录里的 `vault.device.key`（0600），钥匙串条目 `com.mda.assistant` / `vault-db-key-v1` 只在"旧版本用系统安全存储建过库"这一格里被读一次。所以本节按"密钥文件在不在"来分流，而不是按"钥匙串在不在"。

- **症状 A：`vault.db` 还在但打不开**（日志/界面报密钥错误）。先查 `数据目录/vault.device.key` 在不在、是不是 32 字节。这台机器如果是从旧版本升上来的，还有一条活路：`security find-generic-password -s com.mda.assistant -a vault-db-key-v1` 能查到条目 → 重新启动，应用会走"遗留库迁移"那一格（弹一次授权框并要求输登录钥匙串密码，见 §2 第 3 步），当场同意后旧密钥会被原样复制成 0600 文件，此后不再需要钥匙串。macOS 上如钥匙串已被重置、且密钥文件也没了，DB 主密钥即不可恢复——只能走导出容器。
- **症状 B：启动后界面停在"数据库主密钥要落在本机文件"确认页**（`reason=fresh`）。这说明本机**既没有 `vault.device.key`、也没有 `vault.db`**（全新安装），是正常首启，不是故障。此时目录里确实没有写出任何密钥文件；点"退出"保持原样，点"我了解风险，使用本机文件密钥"才会生成并装配。旧库那一格用的是另一种问法（`reason=legacy-vault`，标题"这份保险库的密钥还在系统安全存储里"），别把两种问法当成同一种情况。**装机验收时这两格各有一条打勾动作：全新安装零弹窗见《交付状态与验收》§10 第 24 步第 1 项，遗留库迁移的"点拒绝/点允许"两分支见同一文档 §10 第 15 步（那一步要在数据目录的副本上做，且必须由使用人本人输入登录钥匙串密码——`SecurityAgent` 的框不响应合成辅助功能事件）。**
- **症状 C：`DEVICE_KEY_LOST_VAULT_INTACT`**（日志里出现该错误码；自 2026-10-16 那批构建起窗口会停在失败页「取不到数据库密钥」，如实显示错误码、后端原文与涉及的数据目录；页面上**没有重试按钮**，修好之后要退出应用再重新打开）。含义是"`vault.db` 在，但设备密钥取不到"。成因只剩三种：`vault.device.key` 被删/被移走、这台机器的库是旧版本用钥匙串建的而那次一次性读取失败（条目被删、换了登录账户、或你在授权框上点了"拒绝"）、密钥文件被换成别的机器的副本。程序此时**故意什么都不做**：不生成新密钥、不写 `vault.device.key`、不改名、不备份、不覆盖原条目——因为换掉设备密钥等于让那份 `vault.db` 永久解不开，而这个操作在用户视角是没有反馈的（止损行为自 2026-10-15 起没变过）。正确的恢复顺序：（1）按症状 A 先找回密钥文件或走一次性迁移；（2）找不回来时，**`.mdbak` 备份也解不开**（它的密钥由同一把设备密钥派生，见下一条），唯一还能救的是历史上做过的**"含秘密导出"容器**（口令独立派生）：在新机器或清空的目录上首次启动、当场同意生成一把新设备密钥、**先**把新库建起来并解锁，**再**走「导入/导出 → 导入 → 来源选"口令加密容器"」把数据重建出来（这一侧自 2026-10-15 起真的存在：`container_preview` / `container_commit`，见交付文档 §1-C；在此之前本节写的这条路径只有导出的一半，导入是没有的）；如果连这个容器也没有，那这份数据就是不可恢复的，只能重新开始使用；（3）**不要**为了让应用启动去手工往目录里放 `vault.device.key`——那把新密钥打不开旧库，只会把"还有一条恢复路径"变成"两份密钥都不知道是哪把"。
- 因此：**不要只备份 `vault.db`**。整库加密的密钥材料不在 `.db` 文件里，只拷 `.db` 等于拷回一块打不开的砖；`vault.device.key` 必须与 `vault.db` 一起、且按 0600 权限单独保管（它不在 `.mdbak` 里，也不在任何备份容器里）。
- **但"系统管理 → 备份"那条路也救不了设备密钥丢失**（读代码核实，此前本节把它写成了"含主密钥"，是错的）：`.mdbak` 容器的对称密钥是 `HMAC(db_key, db_key‖salt‖"bkp-v1")`，即**由设备密钥派生**（`backup.rs:25`），恢复时还要用当前 `db_key` 校验恢复出来的库打得开（`backup.rs:229` 的 `PRAGMA key`）。设备密钥一旦不可恢复，这些备份与主库一起变成不可读——它能防的是误删/误改/回滚，不是密钥丢失。**唯一能越过设备密钥丢失的产物是"含秘密导出"的容器**：它的密钥由操作者当场输入的口令经 Argon2id 派生（写出侧 `importexport.rs:835`，`kdf::derive(pw, salt, "mda/export-container-v1")`；读回侧 `importexport.rs:918` 的 `decode_container`，同一条派生参数与 AAD），与设备密钥无关。**所以装机基线里必须把"定期做一次含秘密导出并把它放到别处"写成硬性动作**，光有 `.mdbak` 定时备份是不够的。
- **不要手工编辑或截断 `vault.device.key`**：文件长度不是 32 字节时程序报 `MalformedInput` 并原样保留该文件，**绝不重新生成密钥**（重新生成等于把库锁死）。也不要去删 `keystore-consent.flag`——它只是一个 ISO 时间戳，删掉后旧文件仍可读，但来源会被如实标成"旧版本遗留（没有同意记录）"。`keystore-fallback.flag` 现在含义是"本包使用本机文件密钥"（内容 `file-0600`），不再代表"从系统安全存储降级"。

### 5.3 设备迁移 / 换机

- 支持的路径是"含秘密导出为加密容器 → 新机导入"，**两侧都在后端**（2026-10-15 起）：导出侧 `export_commit` 的 `format: 'container'` 分支勾"含秘密"后必须给一个口令并选 `.mdaexport` 保存路径（不给口令就不让导含秘密的表，判定在后端 `export_commit`）；导入侧 `container_preview` → `container_commit`，填口令 → 选文件 → 看预览（预览只给行数、错误行、冲突行、"含不含秘密"与文件 sha256，**绝不回显任何秘密列**）→ 提交前过一次主密码二次认证。落库走的是与 CSV 同一条逐行路径，所以默认账号、自动建组、标签、冲突策略（跳过/更新/中止）语义与 CSV 导入完全一致。
- ⚠️ **但 2026-10-22 BE 轮起，这条路径在当前构建的界面上点不到**：那三档（容器导出、容器导入、冲突策略「更新 / 中止」）原先只接在齿轮「快捷入口 → 导入/导出」那一屏上，交付方要求"完整的移除这个页面"（见 `交付状态与验收.md` §1-BE），页面与 `api.containerPreview` / `api.containerCommit` 的调用方一起删掉了，**命令、IPC 绑定与 Rust 侧测试一枚没动**。现在账号中心那只弹窗只做 CSV/Excel 导出（可选含明文口令）与 CSV/XLSX 导入，冲突恒按「跳过」。换机因此走**搬文件**这一条：`vault.db` 与 `vault.device.key` 一起按 0600 单独转移（下面第 3 条）；`.mdbak` 备份能救误删误改，救不了设备密钥丢失（§5.2 症状 C）。要把容器这一档接回界面，估计 1.5–2 小时含测试（补进账号中心那只双面弹窗即可，后端不用动）。
- **容器的强度等于那枚口令的强度**（这是这份文件唯一的软肋）：容器密钥**只**由口令派生，所以导出侧有硬闸门——`export_commit` 会先用口令强度策略评估这枚口令（[importexport.rs:896-903](file:///Users/zhouhongbo/Documents/workspace/蒙电信产助手/mon-dian-assistant/src-tauri/src/importexport.rs#L896)：`policy::assess_with(pw, policy::min_length(db))`，不合格直接 `WEAK_PASSWORD`，且**被拒时磁盘上不留下任何文件**），空口令与缺口令则是 `INVALID_INPUT`。测试：`secret_export_passphrase_must_pass_the_password_policy_and_leaves_no_partial_file`。**这一条与主密码无关**：2026-10-17 L 轮起主密码路径已取消全部强度要求（见 §2 第 2 步），`assess_with` 那三项判定（长度、字符类别、常见子串）**现在只剩导出容器口令在读**，两处行为不一致是刻意的，有 `master_password_has_no_complexity_policy_but_container_still_does` 专门守着"别顺手把这里一起放松"。两点要知道：(a) **导出侧的口令输入框下面有实时强度提示**（2026-10-15 补：`api.passwordStrength` + 250 ms debounce，显示"满足策略 / 暂不满足策略，导出会被拒"和四项判定明细；**BE 轮起这一格界面随「导入/导出」页一起移除，`api.passwordStrength` 自此在界面上没有任何调用方（后端命令仍在）；判定与拒绝本来就全在后端 `export_commit`，界面上有没有这句都不改变结果**）。它**只是提示**——不会禁用导出按钮，也不改变任何判定，最终仍以 `export_commit` 里那道后端闸门为准（这样界面无所谓是否被绕过）。**导入侧没有接**，也是故意的：那边压根没有下限可判，接了只会给出一个没有后果的分数。(b) **导入侧不校验强度下限**，这是故意的——短口令导出的老文件必须仍然打得开，否则"恢复"会被自己的策略锁死。另外程序**不区分**"口令错"与"文件被篡改"（都报 `CONTAINER_UNOPENABLE`，避免给外部一个可判定的Oracle），所以打不开时只能两样都查。口令要与文件分开存放：口令丢了，这个容器同样不可打开。
- 提交时会重算整文件 SHA-256 并与预览返回的指纹比对：改了文件（哪怕追加一个字节）报 `CONTAINER_STALE`，要求重新预览；**不会**拿旧指纹静默重试。
- **本包的 DB 主密钥本来就一直是文件**（`vault.device.key`，0600），迁移时必须与 `vault.db` 一起、按 0600 权限单独转移（走加密通道，不要落进任何共享目录或云端同步盘），迁移完成后立即删除传输用的临时副本。旧版本用系统安全存储建过库的，先在这台原机器上完成一次性迁移（§2 第 3 步那一格，需要输一次登录钥匙串密码）再搬文件；搬过去之后新机第一次启动就直接读文件、不会再问钥匙串。
- `keystore-fallback.flag` / `keystore-consent.flag` 是本机的状态标记（前者内容固定为 `file-0600`，后者只是一个 ISO 时间戳），不必（也不应）复制过去——新机第一次启动会重新征询同意。
- 扩展 ID 与新机的浏览器 ID 可能不同，迁移后要重填 `extension_id` 并重装宿主清单。
- 迁移完成后要做的一次抽查：打开一条终端/数据库类凭据，确认**私钥与私钥口令这两列在**（此前含秘密导出会静默丢这两列，2026-10-15 修复，见交付文档 §8 第 21 条）。

### 5.4 备份与恢复校验

| 动作 | 界面/命令 | 说明 |
|---|---|---|
| 创建 | 系统管理 → 备份（`create_backup`） | SQLCipher 一致性备份到临时文件 → `PRAGMA integrity_check` → 整体 AEAD 封装落 `backups/`，审计只记 id |
| 列出 | `list_backups` | 只返回文件名/大小/哈希/时间 |
| 校验 | `verify_backup` | 解封验证完整性，不改当前库 |
| 恢复 | `restore_backup(id, confirmed=true)` | 必须显式确认 + 近期二次认证；恢复前先为当前状态生成回滚备份；恢复后重开连接并**强制锁定**，要求重新输入主密码 |
| 最近备份时间 | `last_backup_at` | 安全状态页显示"从未备份"而不是空白 |

口令/秘密内容从不进入审计、日志或文件名。

### 5.5 管理员离职 / 账号停用

- 系统管理 → 用户与角色 → 停用（`set_user_status`）。停用即丧失全部权限（`rbac::tests::disabled_user_loses_all_permissions`），其历史凭据记录仍在库内但不再可解锁。
- 停用不等于删除数据；离职交接前应先把其负责的目标账号迁移给在职人员（新建凭据 + 停用旧凭据），因为 DEK 是全库共享的，停用无法"抽走"某人独占的秘密。

## 6. 已知运行限制（必须写进交付说明，不能只留在代码注释里）

1. **剪贴板**：复制密码受 `accounts_allow_copy_password` / `copy_password_requires_reauth` 控制；到 `clipboard_clear_after_seconds`（出厂 30 秒）后**只在剪贴板内容仍是本次复制的那串**时才清空。操作系统的剪贴板历史（Windows 历史 `Win+V`、KDE 剪贴板栏、各类同步工具/云剪贴板）不受本应用控制，一旦被系统记录，本应用无法代其删除。安全要求高的单位应在终端策略上禁用系统剪贴板历史。
2. **休眠锁定是近似检测**：以 30 秒定时 tick 的墙上时间跨度（≥4 倍）推断"进程没被调度"，无法区分合盖休眠与进程挂起，两种情况一律锁定并记审计 `session.sleep_lock`。若系统时钟被向回调，判定按"无间隔"处理，宁可不锁也不误判超时。
3. **索引只活于内存**：锁定、超时、切换用户、退出都会清零明文索引；因此冷启动解锁需要重建索引，10k 条实测 291 ms（见交付状态文档的多次测量区间）。
4. **不安全协议默认拒绝**：`allow_insecure_protocols` 出厂 `false`；Telnet/FTP 这类明文终端连接入口需要管理员显式放开，且放开后安全状态页以红色标注"已显式放开"。
5. **遥测为完全离线**：`telemetry` 固定 `disabled`，不存在上报通道。
6. **启动失败页只覆盖“数据/密钥/装配”三类失败**：自 2026-10-16 那批构建起，`setup` 阶段的三类失败（数据目录不可用、取不到数据库密钥、建库或结构迁移失败）都会显示可见的失败页并让进程存活；但 `Builder::build()` 自身失败（配置解析、插件注册、内嵌资源缺失这类“程序装不起来”的故障）仍然没有界面可显示，那时只有日志。失败页刻意不放按钮，因为“就地重试”需要一条可重复执行的装配命令，尚未实现。
7. **schema v5 的名称索引不需要人工干预**：`migrations/0005_target_name_index.sql` 会在旧库启动时自动补建 `idx_targets_name`，不改任何数据行；运维若要抽查，可看启动日志的 `数据库已就绪：schema v5`（v4 备份在新程序上仍可恢复）。
