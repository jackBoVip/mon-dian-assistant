### 0.1 CI 门禁失效的根因（2026-10-26 接上远程后实撞）

F21 补 `ci.yml` 时仓库还不是 git 树，那个门禁**一次都没执行过**，所以没人知道它是红的。接上 GitHub 远程推送后，`verify` 与三端 `release-packages` 在同一步失败：

```
npm ci → EUSAGE: Missing: @emnapi/core@1.11.3 / @emnapi/runtime@1.11.3 from lock file
```

取证过程（判据都在隔离临时目录里跑 `npm ci --dry-run`，**没有在工作区跑 `npm ci`**——它会删 `node_modules`，打断另一会话在跑的 vite/`tauri dev`）：

- 提交里那份 `package-lock.json` 在开发机 **npm 11.6.2**（Node 24.13.0）下 dry-run **通过**（added 213 packages）；
- 同一份锁在 **npm 10.9.2**（`setup-node` 给 Node 22 自带的版本）下 **失败**，报的就是上面那两条；
- 失败对象是 `@tailwindcss/oxide-wasm32-wasi` 的 **bundled 可选依赖**（wasm32-wasi 专用，x64/arm 平台从不真装），npm 10 与 11 对这种结构的校验口径不同。

**处置选择**：把工作流钉到与开发机一致的 npm 11.6.2（Node 24），**不**用 `npm install` 重生成锁。理由：重生成会带进一批 transitive 版本漂移，而这个项目有按产物字节敏感的样式对账守卫（`globalCssEquivalence.test.ts` / `themeContrast.test.ts`），为一条 CI 报错去换一批依赖版本不划算。

**遗留**：`ci.yml` 仍是 `node-version: 22`，同一条错误还在（本轮只改了 `release.yml`）。要么同样钉 npm，要么把 Node 提到 24——这是交付方既有的文件，改它需要点头。顺带一条口径：**门禁类配置（CI/锁/工具链版本）在没有真跑过一次之前，不能记作"已就位"**。

### 0.4 第四批：打包链按平台分叉出的四条（第七~九轮实撞）

1. **rpm 打不出（Tauri 侧缺陷，非本项目代码）**：拆成逐目标调用后 **deb 与 appimage 通过，rpm 单独调用仍报** `duplicate file entry → /usr/bin/mda_fill_host`，证否了"一次传多目标"这个初判。对照 `node_modules/@tauri-apps/cli/config.schema.json`，`DebConfig` 只有 `depends / section / desktopTemplate / *Script` 等键，没有侧车去重开关。处置：rpm 失败只发 `::warning::` 不阻塞，Linux 交付 **deb + AppImage**，日志显式写"rpm 未产出"，不粉饰成通过。
2. **deb 的 `Package` 字段是中文名（待真机定论）**：拆包看 `control` 得 `Package: 蒙电信产助手`，而 Debian Policy §5.6.6 要求包名为小写 ASCII；`DebConfig` 同样没有包名覆写键。**没有擅自改 `productName`**（那是可见的产品决策），也不在 macOS 上臆断 `dpkg -i` 必失败——按《部署手册》§1.2 由 Linux 真机安装定论。候选改法两条：包名由主二进制名派生，或 CI 里重打 `control`。
3. **Windows 后端单元测试从来没跑起来过（本轮最有价值的一条）**：第七轮 `cargo test` 报 `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND`，测试 exe **一加载就死**、一条断言输出都没有。根因不是断言也不是依赖缺失，而是链接期没嵌 **Common-Controls v6 的 manifest**：`TaskDialogIndirect` 一类静态导入只存在于 comctl32 v6，而 v6 只能靠 manifest 的激活上下文加载。`tauri-build` 通过 `cargo:rustc-link-arg-bins` 只给 **bin 目标**的 `resource.lib` 带了清单，lib / integration test / bench 拿不到——于是这条平台上后端测试一直"编得过、跑不了"。
4. **补清单必须按目标类型分开注入**：第九轮把 flag 加到 `--all-targets`，bin 目标立刻撞 `CVTRES: fatal error CVT1100: duplicate resource type:MANIFEST`（随后 `LNK1123`）。最终形态是带清单跑 `--lib --tests --benches`、撤掉清单再跑 `--bins`。附带一条工具链语法坑：`-C link-args=` **只吃一个 token**，写成 `-C link-args=/MANIFEST:EMBED /MANIFESTINPUT:…` 会让 rustc 报 `multiple input filenames provided`（第八轮实撞）。
5. **MSI 装不下中文产品名（第十轮实撞）**：`cargo test` 过了、NSIS 也在跑，`tauri build --bundles msi` 在 WiX 链接期报 `LGHT0311: A string was provided with characters that are not available in the specified database code page '1252'`——生成的 `main.wxs` 用默认 codepage 1252（Latin-1），而 `productName` 是「蒙电信产助手」。`WixConfig` 没有 `codepage` 键，只有 `language`，所以改 `bundle.windows.wix.language = "zh-CN"` 让 WiX 走 936；同时把 msi 降级为**非阻塞**，保证即使这条没修好，本轮也一定有 NSIS 的 `-setup.exe` 可交付，而不是整条 job 红掉什么都不留。改配置后本地复跑读 `tauri.conf.json` 的三处测试（`desktopBundle` / `ipcContract` / `brand-assets`）→ 21 条全绿。**注意这条与 Linux 的第 2 条同源**：中文名在"包元数据必须 ASCII/单字节代码页"的两个格式（deb 包名、MSI codepage）上都会撞，macOS dmg 与 NSIS 因为是 Unicode 通路不受影响。

**跨机不可复现**：同一 commit 两次 CI 的 dmg 哈希不同；CI dmg 的包内主程序是 `c001586d…`(14,233,296 B)、本机是 `abcba99d…`(14,283,280 B)。项目没有可复现构建设施，所以**每批产物各记各的指纹**，判据只认包内二进制 sha256 与真机行为（与《部署手册》§1.1 既有口径一致）。
